# backend/CLAUDE.md

Backend-specific guidance. Run all commands from the **repo root**, not from `backend/`.

## Commands

```bash
PYTHONPATH=backend uv run uvicorn app.main:app --reload --port 8000   # API, Swagger at /docs
uv run pytest -q                                                    # all tests (pythonpath: backend, .)
uv run pytest backend/tests/test_growatt_routes.py -v
pyright --pythonpath .venv/bin/python backend/app backend/solar_core # type check

uv run alembic -c backend/alembic.ini upgrade head
uv run alembic -c backend/alembic.ini revision --autogenerate -m "msg"

PYTHONPATH=backend uv run python -m app.worker --list                # schedule + last runs
PYTHONPATH=backend uv run python -m app.worker --once history        # run one job now
PYTHONPATH=backend uv run python -m app.services.growatt_sync --start 2026-11-05 --end 2026-11-11
PYTHONPATH=backend uv run python -m app.services.daily_summary --dry-run
```

**Two dependency files.** `pyproject.toml` at the repo root is for local `uv` and tests. `backend/pyproject.toml` is what the Docker image installs. Add each new dependency to both.

## Layers

- **`solar_core/`**: pure Pandas/NumPy engine with no FastAPI or SQLAlchemy imports.
  - `ingestion.py`: normalization and the inverter-cloud connectors.
  - `analysis.py`: IEC 61724 PR, string KPIs and faults, returning `AnalysisResults`.
  - `om_management.py`: CM work orders, PM schedule, RCA, PQ and SH&E.
  - `charts.py` (Plotly).
  - `growatt.py`: the Growatt OpenAPI client and `parse_max_records`.
  - `storage.py` is legacy and used only by `test_solar_core.py`.
- **`app/`**: FastAPI.
  - Routes are in `api/routes/*`, ORM models in `db/models.py`, request/response schemas in `schemas/api_schemas.py`.
  - Business logic lives in `services/*`. Keep route functions thin: they call a service and translate its exceptions into `HTTPException` (for example, `GrowattNotFound` becomes 404).
  - Every router is mounted twice, at `/api` and at `/`.
  - Auth is JWT (`app/auth.py`) with two roles. **admin**: everything. **engineer**: only the Growatt plants in `user_plant_assignments` (set by an admin via `/users/{id}/plants`).
    - Every `/growatt/…/plants/{plant_id}/…` route depends on `require_plant_read` / `require_plant_write`; an unassigned plant answers **404** (ids are not revealed). Lists (`/growatt/plants`, `/growatt/live/plants`) are filtered with `allowed_plant_ids` (None = admin = all); the live cache stays fleet-wide.
    - Admin only (`require_admin`): `/users`, `/system/logs*`, fleet module PUT, `/growatt/sync/*`, and the legacy routers (`plants`, `datasets`, `analysis`, `maintenance`, `rca`, `she`), which use the local `plants` table with no link to Growatt plants.
    - Assignments are read from the DB per request, so changes apply without a new login. Any other stored role (the former `viewer`) becomes `engineer` at startup.

**Analysis pipeline** (`services/solar_service.py`):
1. ORM rows become a DataFrame, and `Plant` + `string_specs` become a `PlantConfig`.
2. `run_pv_string_analysis` runs.
3. Results are stored on `AnalysisRun` as JSON columns.
4. `reconstruct_analysis_results` rebuilds them for charts.

**Ingestion**:
- Every source must end up as the long-format columns in `solar_core.models.CANONICAL_COLUMNS`. `normalize_dataframe()` also accepts wide SCADA input (`PV1_U` / `pv1_u` …).
- `POST /plants/{id}/datasets/{upload|fetch|simulate}` → `store_dataset_from_dataframe` → `execute_and_store_analysis`.
- `fetch` with `simulate_if_unreachable` (default false): only when the provider endpoint can't be reached (`solar_core.ingestion.EndpointUnreachable`) does the route store simulator data instead, as `source_type = "simulated"` labelled "Sandbox simulator (… unreachable)", never under the provider's name. A response that arrives but can't be parsed stays a 400.

- **Project phases = Growatt accounts.** Each of the 4 phases has its own token (`settings.growatt_accounts()` → `{phase: token}`).
  - `fleet` lists every account and tags each plant with `growatt_plants.phase`.
  - `history` / `backfill` sync each phase's inverters with that phase's token. Live calls look up the plant's phase in the DB, and `/growatt/live/plants` merges every account.
  - `phase IS NULL` means not yet tagged; those plants use the first configured account. The worker re-runs `fleet` every 6 h while any plant is untagged. It also re-runs `fleet` every 6 h (`FLEET_RETRY`) while the last fleet run was `partial` / `failed` (an account hit 10012, or the run was abandoned): `fleet` is the only job that registers weather sensors and inverter changes, and its 05:30 slot is missed when a long job (e.g. `backfill`) holds the worker past 08:30.
  - Jobs run the accounts in parallel, one thread and one DB session each (`_per_phase`; `WORKER_PARALLEL_ACCOUNTS=false` runs them one by one). A failing account makes the run `partial`, and the run fails only when every account fails. `detail.phases` holds each phase's result.
- **Don't invent values.** If a measurement is missing, return `None` / `null`, not a typical-looking default. The same goes for things with no data source at all (grid import, load): leave them out instead of modelling them as if measured. Label modelled values as modelled: the clear-sky `expected_kw`, the I-V curves, and the peer-relative `pr_pct` / `plant_pr_pct` (strings vs. peers, *not* IEC PR). The measured IEC 61724-1 PR is `kpis.iec_pr_pct` (below).
- **Weather sensors** (`device/env/*`, `services/growatt_weather.py`):
  - device/list shows each as a type-3 device with `device_sn` literally `"env"`; the real key is (datalogger SN, bus address) from `env_list`. `fleet` registers them in `growatt_env_sensors`; `history` / `backfill` sync `env_data` (GET, ≤ 7 days, `perpage` ≤ 100, newest first) into `growatt_env_readings`; `retention` prunes them. Rate limits apply per datalogger.
  - Kept fields: `radiant` (POA W/m²), `envTemp`, `panelTemp`, `envHumidity`, `windSpeed`, `windAngle`. The ~20 others (rain, pressure, …) are always 0 here and are dropped. `timeText` is plant-local; ignore the `calendar` millis (labelled Asia/Shanghai, an hour off).
  - Readings are stored as reported. An unfitted probe reads 0, so a field that is 0 for a sensor all day is returned as null for that day (live: 0 all of the last 7 days).
  - `iec_pr_pct = (E_AC / kWp) / (H_POA / 1 kW/m²)`, null (with `weather.iec_pr.reason`) without a sensor or when irradiance covers < 90 % of the plant's producing 5-min slots. With it, the loss waterfall starts from measured `kWp × H` and uses measured module temperature.
  - Live: `/growatt/live/plants/{id}/weather` (`env_last_data`), cached per sensor like `/latest`. `interval_s` = gap between the sensor's last two different live records (measured from the cached one; null until then; outage gaps outside 30–900 s keep the old value), so the cache expires on the sensor's real rhythm. `stored_until` = `history_synced_until` (newest stored reading); the UI draws live points after it as the chart's tail and re-reads the stored day when it passes the loaded series.
  - **Health flags** (`services/growatt_sensors.py`) are checks, not measurements: each has a `reason`, and none fires without stored data behind it.
    - `probe_missing`: a probe (irradiance, module/ambient temperature, humidity) that reported in the 7 days up to the day reads 0 in every stored reading of the day's daylight. It needs ≥ 24 slots between 09:00 and 15:00. Wind is not checked, because a calm day reads 0.
    - `irradiance_zero_daylight`: irradiance is 0 in ≥ 12 five-min slots between 10:00 and 15:00 in which a stored inverter reading of the plant had `pac_w > 0`. If irradiance reads 0 all day, only `probe_missing` is raised.
    - `stale_history`: computed in the live overlay (`live_row`): the sensor is `online` but `history_synced_until` is > 2 h before its last upload, which is a sync problem, not a sensor fault. Judged only on uploads between 06:00 and 19:00 plant-local (`STALE_DAY_START_H` / `_END_H`), counting from 06:00 at the earliest: many sensors record nothing from dusk to dawn while their datalogger keeps uploading.
- **Google Maps Weather** (`solar_core/google_weather.py` client, `services/google_weather.py`):
  - Modelled by Google for the plant's coordinates, never measured: every response has `modelled: true`, and the UI titles it "Google Weather (modelled)". The Growatt sensor stays the only source of irradiance and IEC PR; Google adds cloud cover, rain, condition, UV, dew point, pressure and visibility.
  - **Daytime only:** `GOOGLE_WEATHER_DAY_START_H`–`_END_H` (06:00–18:00, end exclusive). Only those hours are stored and read, so rain totals and `days_since_rain` count daytime rain only. Live current conditions are fetched only inside the window; at night the last value is served as stale (`refresh_in_s` = until 06:00), or 503 without one. This saves night-time live calls and storage, and halves the history hours each call asks for (see below).
  - Plants share a lookup when their lat/lon round to the same `GOOGLE_WEATHER_CELL_DEG` (0.01°) point: 234 plants → ~229 cells.
  - `google_weather` job (18:15): one `history/hours` call per cell stores today's daytime hours in `google_weather_hourly` (naive plant-local `hour`, idempotent). Each call asks only for the hours back to the latest window start (`history_lookback_hours`: 13 at 18:15; before 06:00 it reaches back to yesterday's window, max 24). Google returns only finished hours, so 18:15 is the first run holding 17:00. The job then re-publishes yesterday's daily docs, about +235 Firestore writes/day. Google's per-day quota "History Hours Usage per day" counts **hours returned, not calls** (24 h calls hit HTTP 429 after 174 cells = 4,176 h); `GOOGLE_WEATHER_HISTORY_HOURS_PER_DAY` (4000) caps the cells a run fetches, hours are counted per billing day as `google_weather_history_hours`, and cells with the oldest stored hour go first so a cut-short run's misses are fetched next time. The first HTTP 429 stops the run's remaining calls; refused calls are not counted against the budget. `history/hours` reaches back only 24 h, so a missed day can't be refetched.
  - Firestore `daily/{day}/plants/{id}.google_weather`: rain mm, daytime cloud %, min/max temp, UV, condition, `rained`, `days_since_rain`, and `slots` `09`/`12`/`17` = `{raining, status_th ("ฝนตก"/"ไม่มีฝน"), condition, precip_mm, precip_prob_pct, cloud_cover_pct, temp_c}` (null = hour not stored yet). `publish_today` (19:30) has today's slots.
  - Budget = the whole free tier, `GOOGLE_WEATHER_MONTHLY_BUDGET` (10,000/month). Every call is counted per billing day (US/Pacific, when Google's month and daily quotas reset) in `external_api_call_counts`. Today's allowance = what is left of the month ÷ days left (today included), so unused calls roll over. Until `google_weather` has run today, live calls leave one call per cell for it. Over the allowance, live serves the last value as stale or answers 503. The job's `detail.usage` shows month used / today's allowance.
  - `days_since_rain` counts back to the last complete day with ≥ 1 mm; it is null when a day without complete data lies in between.
- **Alarm log in SQL** (`services/growatt_alarms.py`): alarms carry Growatt's own start/end times, so they are history, not realtime values. The `alarms` jobs read one inverter-day per call and **replace** that inverter-day's rows in `growatt_alarms` on success (an open alarm gets its `end_time` in place) and stamp `growatt_alarm_syncs` (device_sn, day, synced_at UTC); a failed read keeps the old rows. Inverters are swept never-read / oldest-read first; 3 consecutive 10012s end that account's sweep. No sync row = not read yet, which the API and UI report as such (never as zero alarms). `retention` prunes both tables with the readings.
- **Live string check** (`services/live_string_check.py`): `/live/plants/{id}/latest` adds `data.string_check`, each string judged against the other strings of its inverter **in the same record** (memory only). Current vs. the inverter median (open strings left out): ≤ 0.3 A = Critical (open string), ≤ −40 % Critical, ≤ −15 % Warning. Voltage only per module, and only when every string has a String Layout count (otherwise shorter strings would look faulty). Mismatch is judged only when the median is ≥ 3 A; below 1 A there is no verdict. A Warning / Critical must hold in the 6 newest records (≈ 30 min; the five older ones come from the same `max_data` call as `previous_strings`, which the route drops before answering), else it is downgraded: a passing cloud shadow makes part of an array look 50 % low for one record, and in a fast cloud-to-sun ramp an MPPT can drift towards open-circuit voltage for 15 min (Nong Bua 13 Nov 09:56–10:06) and recover by itself. Only wired inputs count (`growatt_overview.wired_inputs`: layout rows + current seen in 30 days, cached 6 h); with wiring unknown, a 0 A input gets no verdict. The UI's plant status uses this, not the stored-day `_classify_strings`.
- **Fault log:** `/growatt/live/plants/{id}/alarms?day=&days=7` reads `device/max/alarm_data` (POST, one inverter-day per call, `page`/`perpage`, run in a small thread pool) for the `days` ending at `day`. It is memory-only like every live value: each inverter-day is cached, today's for `GROWATT_LIVE_TTL_S` and a past day's for 6 h. The UI shows it in the "Growatt Fault Log" panel (Plant Overview, and per inverter on Inverters).
- **Strings differ in length.** Growatt doesn't report modules per string; engineers enter them in `growatt_string_layouts` (`GET/PUT /growatt/plants/{id}/string-layout`, UI: String Layout tab). `_classify_strings` compares energy per module (per kWp when every `module_wp` is set) and voltage per module only when *every* string of the inverter has a count; otherwise it compares raw values. Each string carries `peer_basis` (`raw` / `per_module` / `per_kwp`); current is never scaled (series string). A string with `module_wp` null uses the **fleet module** Wp (`services/fleet_settings.py`, global setting in SQL `app_settings`, `GET/PUT /growatt/fleet-module`, UI: Settings; default ZNShine ZXM7-UHLDD144 570 W). Saving it publishes Firestore `config/fleet_module` right away (1 write, within the budget); the publish jobs also carry it with the registry. Saving a plant's layout likewise publishes that plant's `inverters/{sn}` docs, which carry `strings: [{string_no, modules, module_wp}]` (key absent while an inverter has no layout).
- **Record interval is mixed** (mostly 5 min, some inverters every 1–4 min). Integrate energy with `_integrate_kwh`, never `sum × 5 min`. To build a plant curve, average each inverter within its 5-min slot first, then sum across inverters. Inverters report every 4–5 min, so a record often drifts past a slot edge: an inverter with no record in a slot keeps its own last slot value for up to `MAX_GAP_H` (10 min, the same limit energy integration credits), only in slots that exist anyway; never longer, never another inverter's value. Each overview `timeseries` slot carries `inverters` (in the sum) and `held` (of those, held). Checked on 12 Nov: curve energy = 95–102 % of measured yield on all 42 plants with data (before: 71–101 %).
- **Daily yield = `eac_today` from the day's last record.** The counter keeps yesterday's total for a few minutes after midnight, so `MAX()` is wrong.
- **MAX inverters:**
  - String data comes from `device/max/max_data` (POST, ≤ 7 days, `perpage` ≤ 100, newest first).
  - String *n* is on MPPT ⌈n/2⌉. `vString` is the MPPT voltage, while `currentString` is per string.
  - String rows are kept only while `ppv > 0`, because PID recovery holds about 60 V at night.
  - `device/list` returns each MAX twice (type 1 and type 4); merge them by serial.
  - Name / rated power / firmware (`alias`, `normalPower`, `fwVersion`, `innerVersion`) and the inverter **settings** (`activeRate` power limit %, `reactiveRate`, `pf`, `pfModel`, `exportLimit`, `exportLimitPowerRate`, `onOff`) come from `device/max/max_data_info` and are stored on `growatt_inverters`. Settings are configured values, not measurements; the UI flags `active_rate_pct < 100` as curtailed and `on_off = 0` as switched off. Growatt often answers the whole settings block as 0 (on 15 Nov: all 629 inverters, while producing at full power); `parse_max_info` stores a block with `activeRate` and `pf` both 0 as null (not read), never as 0 % / off. The `fleet` job sweeps each account once per run, never-read then oldest first, for entries older than `INFO_REFRESH_HOURS` (20). `max_data_info` is tightly rate limited (about one call per account every few minutes): the first 10012 ends the sweep, and the rest wait for the next run. An answer without data is not stamped as read.
  - **Power limit from `readPower`** (`new-api/readPower`, POST with query params, replies `{code, data, message}`; `GrowattClient.read_power`): the active power limit read from the inverter itself, stored as `power_limit_pct` / `power_limit_read_at` by the daytime `power_limits` job (10:40). `GrowattInverter.active_limit_pct` = `power_limit_pct` when read, else `max_data_info`'s `active_rate_pct`; the decision rules (`growatt_daily._limit_w` / `_limited`) and `settings.active_rate_pct` in the API use it (`settings.active_rate_source` = `read_power` / `max_data_info`). It answers only while the inverter runs and some dataloggers never pass it on (15 Nov 2026 sweep: 488 / 629 answered, 107 code 18 `READ_DEVICE_PARAM_FAIL`, 34 code 5 `DEVICE_OFFLINE`, grouped by site): a refusal keeps the stored value and its read time, never writes 100. Once per inverter per `POWER_LIMIT_REFRESH_HOURS` (20), oldest first, 2 s apart (no 10012 at that pace over the fleet), 3 × 10012 in a row end the account's sweep.
  - **Growatt's own energy, curve and registry extras** (docs/plans/growatt-new-endpoints.md, `services/growatt_energy.py`): `plant/energy` → `growatt_plant_energy_days`, `device/inverter/day_energy` → `growatt_inverter_energy_days` (both kept indefinitely), `plant/power` → `growatt_plant_power` (pruned by `retention`). Finished days only (today is realtime). Shown next to, never instead of, our integrated figures (a day figure above `MAX_GROWATT_KWH_PER_KWP_DAY` 10 × kWp is withheld as a Growatt glitch, `growatt_implausible`): `/plants/{id}/power` `growatt_timeseries` and `daily[].growatt_energy_kwh` / `growatt_inverters_kwh`. `fleet` also reads `plant/details` (timezone, address, Growatt's inverter / datalogger counts; every `DETAILS_REFRESH_DAYS` 7) and `new-api/queryDeviceInfoParam` (`device_model`, `datalogger_model`, `rated_power_w`; every `PARAM_REFRESH_DAYS` 30); a blank answer never erases a stored value. Rate limits of these were not measured: 3 × 10012 in a row end an account's sweep, the next run resumes (missing / oldest first).
  - **`device/max/maxs_data`** (used by `/growatt/live/inverters/snapshot`, `GrowattLiveService.inverter_snapshot`: chunks of 50 sorted serials per account, one cache key per chunk, swept like the sensor status, `INVERTER_SNAPSHOT_TTL_S` 300 / `INVERTER_SNAPSHOT_SWEEP_PER_REQUEST` 4, memory only; tested 15 Nov 2026, phase 1, `backend/scripts/probe_growatt_endpoints.py --maxs-batch`): POST `maxs` = comma-joined serials, `pageNum`; answers the newest full `max_data` record (278 fields, strings included) per serial, about 50 serials per page, ~1 s per call. Rate limit is per account, by window: a burst of 4 calls in 8 s (17, 50 and 100 serials, the last in 2 pages) all answered, then every call was 10012 at +60 s and +180 s, and all answered again at +300 s (the refusals did not restart the wait). So one fleet-wide snapshot per account every ≥ 5 min; it gives only the newest record (the live string check needs the 6 newest, the chart the power tail, so `max_data` stays). Inverters silent for months answer their old record (June 2025), so its `time` must be shown, never taken as now. It does **not** share `max_data`'s per-inverter window (15 Nov 13:43, one burst: `max_data(W)` ok → `maxs_data([W])` ok; `maxs_data([V])` ok → `max_data(V)` ok; `max_data(W)` again → 10012): a snapshot neither waits for nor uses up the live calls' window.
  - `/live/plants/{id}/latest` also returns, from the newest `max_data` record:
    - `grid`: phase/line V, A, `pf`, `reactPower`.
    - `diagnostics`: `faultType`, `faultCode1/2`, `warnCode1`, `warningValue1-3`, `pidFaultCode` and `StrBreak`; `pvIso`, where 65530 = no reading → null; `temperature2/3`, assumed to be IPM/boost; `afciStatus` and `afciPv1/2`; `gfci`; `r/s/tDci`; `timeTotal` in seconds → `time_total_h`.
    - `mppt_energy`: `epv{n}Today/Total`, kWh.
    These are live only and never stored. Units of GFCI/DCI/AFCI are Growatt's own and are shown as reported.
- **Timestamps:**
  - Growatt reading tables are naive plant-local (Bangkok) time.
  - App bookkeeping columns (`sync_runs`, `published_docs`, `synced_at`) are UTC. SQLite drops tzinfo, so store UTC and read naive values back as UTC (`jobs._aware`).
- **SQL must run on SQLite and Postgres.** Use SQLAlchemy expressions; no `strftime` / `date()` in raw `text()`. Time bucketing happens in Python.

## Logging (System → Logs)

- **Use `logging.getLogger(__name__)`; never `basicConfig`.** `app/logging_db.setup_logging(source)` sets up the console and `DbLogHandler` (`source` = `api` from `main.py`'s lifespan, `worker` from `worker.py`, `cli` from the CLI entry points). Records at `LOG_DB_LEVEL` and above go to SQL `app_logs`; `sqlalchemy.*`, and `urllib3` / `httpx` / `httpcore` / `requests` below WARNING, are never stored (their lines carry full URLs).
- **Everything stored is redacted** (`redact()`): the exact token / key / secret / DB-password values from settings, plus `?key=` / `token=` / Bearer / Postgres-URL patterns. Still, never log a secret or a live measurement on purpose: logs are bookkeeping, not data.
- **Flushing:** the worker and CLIs flush from a daemon thread every `LOG_FLUSH_INTERVAL_S`, at once after an ERROR, and at exit. The API has no thread (Cloud Run cuts the CPU after the response): `app/api/request_log.py` flushes before each response returns. A failed insert is printed to stderr and dropped, never re-logged.
- **Context:** `jobs.execute` sets `run_id` / `job` (context vars) for the run, and logs "job X started / finished"; `_per_phase` threads copy the context. The request middleware sets `request_id` (also the `X-Request-ID` header) and logs only 5xx / unhandled exceptions (with traceback) and requests slower than `LOG_SLOW_REQUEST_MS` (WARNING; `/growatt/live/*` only INFO, since there the wait is Growatt / Google refilling an expired live cache). `app.audit` logs failed logins (name only) and admin actions (job queued, user created/changed (field names only)/plants set, fleet module saved).
- **Volume:** the per-inverter line in `sync_history` is DEBUG; keep per-item lines at DEBUG and summaries at INFO.
- `/system/logs` (`?level=&source=&job=&run_id=&q=&since=&until=&before_id=&after_id=&limit=`, newest first; naive times = Bangkok; default window 24 h, a `run_id` alone = the whole run) and `/system/logs/summary` are in `services/system_logs.py`.

## Worker and jobs

`app/worker.py` runs as one process (docker service `growatt-worker`); never start it inside uvicorn.

- Daily jobs fire only within 3 h after their slot.
- `services/jobs.py` holds the job bodies and the run log / lock (`sync_runs`).
- `GET /growatt/sync/status` and `POST /growatt/sync/{job}` cover the API side. **The API only queues a run** (`status = queued`); the worker starts it on its next tick (≤ 1 min). Never run jobs inside the API: on Cloud Run the CPU is cut after the response. A job that's already queued or running returns 409; a queued run nobody picks up within 2 h is marked failed.
- **Run `publish_today` at most twice a day.** An open day changes on every run, so each run rewrites about 250 Firestore documents.

## Production (`APP_ENV=prod`)

- Startup refuses to run without `ADMIN_PASSWORD` (≥ 12 chars) or with the default / short `JWT_SECRET_KEY`.
- Only one admin is seeded, from `ADMIN_USERNAME` / `ADMIN_PASSWORD`. Changing the secret resets that admin's password. Demo accounts still on their demo password are disabled, and no demo plant data is created (`SEED_DEMO_DATA` overrides).
- Every data router requires a signed-in user (`main.py`); only `/auth/login` and `/health` are open. Files (CSV templates) are downloaded by the UI with `fetch` + token, not plain links.

## DB and migrations

- `DATABASE_URL` defaults to SQLite at `data/solar_fullstack.db`; Docker uses `postgresql+psycopg`.
- Startup (API and worker) calls `ensure_schema` (`db/session.py`): `create_all` plus `_ADDED_COLUMNS`, which adds new columns to existing tables. New tables and listed columns appear without Alembic. Still add a hand-written migration under `alembic/versions/` (chain `down_revision`) for Postgres.
